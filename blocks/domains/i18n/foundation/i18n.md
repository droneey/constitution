# Internationalisation

## user-facing-text-from-catalog · MUST
Every string a user reads comes from the message catalog, by key; none is written in code.

| Why | Check | Tags |
|---|---|---|
| text in code cannot be translated or reworded without a code change, and it is found only by reading every file. | review | [ux] |

## messages-take-named-parameters · MUST
A message takes its values as named parameters inside it; a sentence is never built by joining strings.

| Why | Check | Tags |
|---|---|---|
| languages order words differently, so a sentence joined in code cannot be translated. | review | [ux] |

## plural-forms-by-locale-rules · MUST
Plural and ordinal forms are selected by the locale's CLDR rules, inside the message, never by a condition in code such as "the count is one".

| Why | Check | Tags |
|---|---|---|
| many languages have more than two plural forms, and code written for one language gets the others wrong. | review | [ux] |

## values-formatted-by-locale · SHOULD
Numbers, dates, currencies and lists are formatted by the locale.

| Why | Check | Tags |
|---|---|---|
| `1,000.50` and `1.000,50` are the same number to different readers; a fixed format misleads one of them. | review | [ux] |

## Requirements for implementation

What any message library must provide.

## i18n-typed-keys · SHOULD
A missing or misspelt key fails the check.

| Why | Check | Tags |
|---|---|---|
| a missing key shows the user a raw key instead of text, and only a check finds it before they do. | review | [ux] |

## i18n-lazy-locales · SHOULD
Each locale's catalog loads on demand.

| Why | Check | Tags |
|---|---|---|
| a user downloads only the language they read. | review | [performance] |
