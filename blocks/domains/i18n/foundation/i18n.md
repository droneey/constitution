# Internationalisation

## user-facing-text-from-catalog · MUST
Every string a user reads comes from the message catalog, by key; none is written in code.

| Why | Check | Tags |
|---|---|---|
| text in code cannot be translated or reworded without a code change, and it is found only by reading every file. | review | [ux] |

## messages-take-named-parameters · MUST
A message takes its values as named parameters inside it; a sentence is never built by joining strings.

| Why | Check | Tags |
|---|---|---|
| languages order words differently, so a sentence joined in code cannot be translated. | review | [ux] |

## module-level-text-holds-the-message · MUST
Text defined outside a render — an option list, an enum's labels — holds the message, never its translated result, and is translated where it is shown.

| Why | Check | Tags |
|---|---|---|
| a translation taken when the module loads keeps the locale of that moment, and a later switch of language misses it. | review | [] |

## plural-forms-by-locale-rules · MUST
Plural and ordinal forms are selected by the locale's CLDR rules, and the variants of a sentence that changes with a value — a gender, a role, a status — by a select, all inside the message, never by a condition in code such as "the count is one".

| Why | Check | Tags |
|---|---|---|
| many languages have more than two plural forms, and code written for one language gets the others wrong. | review | [ux] |

## values-formatted-by-locale · SHOULD
Numbers, dates, currencies and lists are formatted by the locale.

| Why | Check | Tags |
|---|---|---|
| `1,000.50` and `1.000,50` are the same number to different readers; a fixed format misleads one of them. | review | [ux] |

## formatters-take-the-active-locale → values-formatted-by-locale · MUST
Every formatter of numbers, dates and lists is given the active locale, never left to the runtime's.

| Why | Check | Tags |
|---|---|---|
| the runtime's locale differs between the server and the client and between a spec and production, so the same value prints differently. | review | [ux] |

## pseudo-locale-in-development · SHOULD
A pseudo-locale — accented, longer, optionally right-to-left — runs in development.

| Why | Check | Tags |
|---|---|---|
| it shows text written outside the catalog, text cut by its box, and sentences built by joining. | review | [ux] |

## ambiguous-messages-carry-context · SHOULD
A short or ambiguous message carries a comment or a context for its translator.

| Why | Check | Tags |
|---|---|---|
| "Open" is a verb or an adjective; a translator who cannot see the screen guesses. | review | [ux] |

## Requirements for implementation

What any message library must provide.

## i18n-typed-keys · SHOULD
A missing or misspelt key fails the check.

| Why | Check | Tags |
|---|---|---|
| a missing key shows the user a raw key instead of text, and only a check finds it before they do. | review | [ux] |

## i18n-lazy-locales · SHOULD
Each locale's catalog loads on demand.

| Why | Check | Tags |
|---|---|---|
| a user downloads only the language they read. | review | [performance] |
